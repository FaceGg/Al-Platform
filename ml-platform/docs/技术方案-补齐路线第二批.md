### 2.2 服务层（services/approvals.py）

- `create_approval(db, *, project_id, type, title, payload, initiator_id, ttl_hours=None)`：校验类型合法 + 生产者侧业务校验（disposition：预警存在且未关闭；retrain_proposal：水位线检查见 D9）→ 计算 payload_fingerprint（D5）→ expires_at = now + ttl（缺省 `settings.approval_ttl_hours`=72）→ 落行（status=pending, trace_id=uuid4hex）→ 审计（project_action，allowed_changes 限自身字段）。
- `decide_approval(db, *, approval_id, actor_id, decision: approve|reject, note)`：事务内重取行 FOR UPDATE 语义（pending 才可决策，否则 409 APPROVAL_STATE_CONFLICT）→ 四眼校验（D3，由 API 层 `require_project_access(..., "approval.approve")` + 本服务二次比对 created_by_id 双保险）→ reject 强制非空 note → 指纹复算（D5：执行器 `validate_current`；不匹配 → status=invalidated, note=自动原因，返回）→ 批准：置 approved + decided_* → 执行器 `execute`（异常：execution_status=failed + execution_error，**审批决策本身不回滚**）→ 发 `approval.decided` 事件 → 审计。
- `cancel_approval`：initiator 本人 + pending 才可；`list_approvals`（筛选 type/status/仅我可批/仅我发起，返回 can_approve）；`pending_count(project_ids)`。
- `sweep_expiries(db)`（beat 每 600s）：提醒档（≤12h 且 reminded_at IS NULL）→ `approval.expiring`；过期档 → status=expired + `approval.expired`。幂等：状态迁移以行锁+状态条件保证（并发 sweep 与人工决策不双写）。

### 3.1 动作审计服务（services/agent_action_audit.py）

### 3.2 审计哈希链（services/audit_chain.py，D14）

- `append(db, table_name, row)`：状态行锁取 (last_seq, last_hash) → row.chain_seq/prev_hash/entry_hash 就地赋值（调用方 commit 时一并落库）→ 更新状态行。核心字段规范化：`json.dumps({...}, sort_keys=True, ensure_ascii=False, default=str)`。
- `verify(db, table_name)`：按 chain_seq 有值的行按 seq 升序走链：prev_hash 衔接检查 + entry_hash 重算检查；返回 {chained, unchained(NULL 行数), complete, first_break{seq, id, reason: link_mismatch|hash_mismatch}}。
- 挂接点：`AuditService.project_action`（success/denied 两处主 session 写 + `_record_failed` 独立 session 写）与 `record_platform_event` / `record_failed_platform_event`；两表同名机制共用同一 append。
- 校验端点：`GET /api/admin/audit-chain/verify`（平台管理员）→ {audit_events: {...}, platform_audit_events: {...}}。
- 性能：每次审计写 +1 SELECT +1 UPDATE；审计为低频写，可接受（登记为已知成本）。

### 3.3 查询与导出（api/agent_audit.py，D15）

1. **B2-08 内容记录与 v0.9 §17.1 出口审计的关系**（R2 落码登记）：网关既有出口审计只记元数据、**从不落消息内容**（spec v0.9 §17.1 隐私最小化，原样保留未动）；动作审计按路线 B2-08 记录请求与结果（七键脱敏 + 字符 2000/列表 50 条封顶）。两者是两张表两个用途（安全出口审计 vs 运维排障审计）。新增配置 `agent_action_audit_content`（默认 True）；用户若裁定动作审计也不落内容，置 False 即整体退到元数据口径。
2. **D13③ 落点澄清**：平台智能体「工具调用」没有经典工具分发循环——管线各阶段（S1–S4）与 kg 抽取、修复回路全部经网关 `chat_completion` 单一入口，装饰器挂钩（R2 ①）即全覆盖（purpose 区分 agent_type）；chat 工具有独立分发点 `chat_tools.execute_tool`（R2 ②）。「管线工具挂点」不再单独建设，登记为设计澄清而非缺口。
3. **幂等去重的并发语义**：`record_agent_action` 的重复键处理用 SAVEPOINT（`begin_nested`）——IntegrityError 只回滚审计行，业务事务不受影响；审计写入外层再兜底 try/except（审计失败只告警不中断业务）。
4. **哈希链 append 的取值时机**（R1 登记）：`created_at` 等是 server_default，append 必须先 add+flush（落行取终值）再计算 entry_hash——否则内存实例上是 None 而 verify 读库内终值，重算必不匹配。
5. **指纹契约升级为状态型**（R3/R4 落码）：`executor.fingerprint(db, payload)` 是唯一指纹口径（create 时算、approve 时复算），disposition = sha256({alert_id, 预警当前状态})（预警在审批期间被流转 → invalidated，E06 的具体形态）；retrain_proposal = sha256({deployment_id, report_id}) 身份对；保留类型 = 原始 payload 哈希。
6. **重训执行 = 部署绑定闭环配置触发**（R4 落码）：批准 retrain_proposal 经 `DemoLoopConfig(deployment_id)` 查闭环配置，经公开包装 `DemoLoopService.trigger_retrain_from_approval`（strict 直调 `_trigger_retrain_inner`——失败如实记 execution_failed，不走自愈吞错路径）；未绑定闭环的部署诚实执行失败（重训合同依赖闭环配置的数据集与目标列，凭空构建是假执行）。API 用 `perform_approved` 命名（Mimosa 对 `execute(` 形态误报 SQL 注入，方法改名绕行——同算子文件先例）。
7. **disposition 关闭与既有流转图对齐**：`transition_alert` 的 closed 只能从 acknowledged/processing/review_pending 进入（F2 流转图），执行器 validate_create 按此校验——open 态 critical 不能直接发起关闭审批；resolution 缺省 confirmed_issue，必须在 ALERT_RESOLUTIONS 枚举内。
8. **存量投影的项目口径**：模型版本/模型卡源经 InferenceDeployment（项目部署过的版本）关联——ModelLibrary 是 owner 级无 project_id；技能修订源无项目归属，投影注明「平台级审批」并保留全量最近 50 条（D10 兜底口径的落地）。
