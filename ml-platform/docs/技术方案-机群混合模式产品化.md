## 1. 使用语义：A/B 在现场操作中的区别（决策摘要）

| 场景 | 方案 A 分片独立 | 方案 B 全局共享+设备级标定 |
|---|---|---|
| 首次建模（N 台同型设备） | 每设备各自建模（平台分片链已支持：选工况列一次任务产出 N 模型） | 所有设备数据合并一次任务 → 1 个共享检测器 + 每设备 1 份标定表（**联合训练链待产品化**） |
| 新设备接入（仅 200 行标定数据） | 无可用模型——走 M9 迁移借模型（跨工位形态差异大时不适配，fleet_fpr 实测 1.0） | **200 行标定即得**（全局主体天然懂共有形态）——冷启动核心优势 |
| 某工位漂移 | 重训该工位模型（其它不受影响） | 重标定该工位阈值表（秒级）；形态级变化才重训全局 |
| 检出质量 | 本工位专属形态精度最高 | 共有形态一致；本工位特有形态可能漏（unfit 护栏兜底） |
| 资源 | N 模型 + N ONNX（线性涨） | 1 模型 + N 份 KB 级标定表 |

**不互斥**：方案原文 §7.5 设计即「B 主 + A 兜底」——unfit 设备降级独立建模（方案 A 形态保留为降级路径）。

## 3. 产品化设计

### 3.1 G1：AutoML 新建弹窗——工况列与机群共享模式（前端）

**位置**：AutoMLPage 新建弹窗 → 无监督范式选中后，污染率字段之后新增两个字段：

1. **工况列**（Select，可空）：选项 = 当前数据集的**非数值列 ∪ 低基数值列**（基数 ≤ 200 的列，设备号/工位号/程序号形态）；选中后提示「将按该列分片训练 N 个模型」
2. **机群共享模式**（Switch，默认关；仅工况列已选时显示）：
   - 开 = `fleet_mode: "shared"`（联合段全局模型通配兜底 + unfit 工位不挂载）
   - 关 = 分片独立（每工位独立模型）
   - 文案：「开启后全工位共享一个检测器模型，每工位独立标定阈值；新工位无需建模即可通过标定接入（推荐同型设备群）」

**payload**（isAnomaly 分支追加）：

```ts
...(conditionColumn ? { condition_column: conditionColumn } : {}),
...(conditionColumn && fleetShared ? { fleet_mode: "shared" } : {}),
```

**校验**：机群模式开启但未选工况列 → 提交前警告拦截。

**类型**：`AutoMLRunPayload` anomaly 变体加 `condition_column?: string; fleet_mode?: "shared"`（api/training.ts）。

**估算**：表单两控件 + payload 三行 + 类型两字段 ≈ 60 行 + 单测 2 例。

### 3.2 G2/G3：M6 档 1 API + 模型库重标定入口

**API**（model_registry router）：

```
POST /api/model-versions/{version_id}/recalibrate-labels   ← 现网已落地（第六轮 e112119f）
  body: { labeled_artifact_id: UUID, feedback_marks?: dict, mount?: bool }
  → label_recalibrate_version(...)（门槛 fail-closed：M6_GATE_NOT_UNLOCKED 映射 409 带 confirmed/50 计数）
  → 返回 { version_id, new_threshold, old_threshold, gate, false_alarm_report, next_steps, ... }
```

> **路由名与请求体分歧（需拍板，建议沿用现网）**：本方案原稿提 `label-recalibrate` + `positive_label`，而第六轮已上线 `recalibrate-labels` + `feedback_marks`（与既有 `recalibrate-device` 命名族对齐，且 `feedback_marks` 正是服务层 `apply_feedback_marks` 消费、且能与数据集自带 `feedback` 列合并的形态）。**建议沿用现网 `recalibrate-labels` / `feedback_marks`，改本方案提案而非改线上路由**（线上已有测试与错误码映射）。`positive_label` 想表达的「标签列名」语义已由服务层 `confirmed_morphology_clusters` 覆盖。

**前端**（模型库详情页版本操作区，approval_status=approved 且 output_schema.task=anomaly 时显示）：

- 「标签阈值重标定（M6 档 1）」按钮 → 弹窗选标注数据集（数据管理列表）→ 调 API → 结果展示（新旧阈值对比 / confirmed 计数 / 误报形态报表 / 派生版本链接）
- M6_GATE_NOT_UNLOCKED（409）→ 提示「confirmed_fault ≥50 未达，当前 N 条——继续标注积累」

**挂载联动**：重标定版本（pending）→ 复用既有审批流（approve）→ `add_fleet_shard_to_deployment` 挂到目标部署（condition_value=设备号）。

**估算**：API 40 行 + 前端弹窗组件 120 行 + 单测 3 例。

**API**：

**估算**：API 30 行 + 前端按钮 40 行 + 单测 2 例。

### 3.4 G5：FleetShardPanel 补 per-device 运行期报警率列 —— **第六轮已修，本项闭环**

`fleet_overview` 返回 `running`（rows/alerts/alert_rate，分片化统计）——FleetShardPanel 表格已加「运行期报警率」列（无数据显示「—」），前端类型 `FleetShardRunning` 已补。

> **⚠️ 读取容器方向的更正（重要）**：原稿写「统一从 `conversion_metadata.recalibration` 读」——**方向反了**。重标定载荷写在 `version.metrics["recalibration"]`，`conversion_metadata` 里没有该键；只从 `conversion_metadata` 读会让「回测 AUC」恒为 null（即第四轮审计登记的原始缺陷）。**正确口径 = metrics 优先、conversion_metadata 回退**（`anomaly_device_calibration.py:597-599` 现网实现即为此），保留回退是为兼容早期把载荷写进 `conversion_metadata` 的版本。

**本项剩余工作量：0（已闭环）**。

## 4. 现场使用流程（产品化后的完整操作路径）

### 场景：4 台同型设备上线机群检测

1. **机群基线**：数据管理上传各工位数据（或合并表）→ AutoML 新建 → 无监督范式 → 选工况列（STATION）→ 开机群共享模式 → 运行 → 产出：4 份设备标定 + 1 份全局模型（fleet_shared 联合段）+ 4 份工位独立模型（A 兜底）
2. **部署**：模型库审批 → 挂载 4 个 fit 工位 targets（unfit 工位不挂）
3. **新设备接入**：新工位采 200 行**纯正常**数据上传 → 模型库「**设备重标定（M9）**」`POST /api/model-versions/{id}/recalibrate-device` → fleet_fit 判定（compatible → 挂载 / unfit → 提示独立建模）。
   > **语义更正（原稿混用了两条路径）**：原稿此步写「标签阈值重标定（M6 档 1）」是错的——M6 档 1 需要**带标签的** confirmed/false_alarm 回流行且门槛 confirmed_fault ≥ 50，用 200 行纯正常数据必然 `M6_GATE_NOT_UNLOCKED`。新设备冷启动走 **M9 设备重标定**（纯正常数据 → fleet_fit），M6 档 1 属于第 5 步（标签积累后的阈值再校准）。两条路径入口必须在界面上分开。
4. **监控**：闭环详情页 FleetShardPanel（per-device 报警率 + PSI）
5. **M6 解锁后**：confirmed≥50 → 档 1 阈值重标定 `POST /api/model-versions/{id}/recalibrate-labels`（**带标签**回流集，门槛 fail-closed）
