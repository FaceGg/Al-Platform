# 技术方案：知识图谱五阶段流水线（LLM 抽取 + Neo4j 投影 + 融合审核 + 图应用）

> 2026-11-20 立项，当日交付。背景与用户决策链见 DEVELOPMENT_PLAN.md 2026-11-20 条目。
> 技术路线为用户四项拍板：**LLM 抽取 / 引入 Neo4j / 自动融合+人工审核 / 五阶段一次到位**。

## 0. 决策记录

| 决策点 | 选择 | 关键理由 |
|---|---|---|
| NER/RE 引擎 | LLM 抽取（平台 LLM 网关） | 零新基建、领域语义类型（对比 jieba 词性桶）；BiLSTM-CRF/BERT 需 BIO 标注数据+transformers 全栈（探查结论最低 2-4 周） |
| 三元组存储 | Neo4j 投影镜像 + PG 事务主源 | PG 已验证 7,915 实体/67 万边规模；投影幂等（MERGE by entityId）避免双写一致性黑洞；Neo4j 承担多跳/路径/关联查询 |
| 知识融合 | 确定性归并自动执行 + 模糊/冲突进人工审核 | 同名/别名归并证据充分可自动；语义对齐与属性冲突裁决需人担责 |
| 旧规则引擎 | 保留为「快速抽取」通道 | method="rules"/"llm" 双层并存，重建互不影响 |

## 2. 抽取引擎（阶段 2）

- **契约**：`KgUnitExtraction`（entities[{name,type,aliases,attributes[{name,value,evidence}]}], relations[{source,target,type,evidence}]），pydantic 校验 + `parse_llm_json` 容忍围栏/截取
- **修复回路**：契约失败 → 坏输出+校验错误喂回重试一次 → 仍败则 raw_first/raw_retry 各截 1500 字符留档进单元结果 `error`
- **提示词**：S1 范式——输出骨架逐字示例 + 类型词表 + 条数上限（实体≤20/关系≤15）+ chunk 文本引述块隔离 + 显式 max_tokens（`kg_llm_max_tokens`=3000，勿吃 2000 缺省）
- **任务化**：`kg_extraction_jobs` + celery `ml_platform.execute_kg_extract`（broker 不可用降级进程内线程）；逐 chunk 落 `kg_unit_results`（幂等键 kb_id+chunk_id+content_hash）→ **断点续抽**：重跑跳过已成功单元；取消标记逐单元检查；`kg_llm_max_chunks`=120 成本护栏；`kg_llm_time_budget_seconds`=1800
- **落库语义**：聚合全部 ok 单元 → 清 `method="llm"` 层 → 实体链接（与 manual/rules 存活实体归一化同名/别名命中时复用 id 不新建）→ 批量插入；类型/关系词表强制 coerce 到本体（兜底「概念/相关」）
- **规则层同批升级**：`_clear_auto_layer` 按 method 清层；规则抽取同样接入实体链接复用（`kg_names.existing_entity_index`）；`_normalize_name` 委托 `kg_names.normalize_name`（ASCII 词含大写 casefold，两层一套归一）

## 3. 知识融合（阶段 3）

```
抽取完成 → Pass1 同名/别名归并（自动，accepted 留痕）
         → Pass2 属性冲突（同实体同属性跨文档异值 → pending）
         → Pass3 difflib≥kg_fusion_fuzzy_threshold(0.92) 候选对
                → LLM 批量仲裁（same/canonical/reason；LLM 不可用→全部进人工队列）
                → pending 合并建议
人工审核 → accept：merge_entity=重指关系→(winner,loser,type) 去重保留最高权重
                → loser 原名与别名并入 winner.aliases → 属性并集
                → loser.merged_into=winner（存活过滤处处生效）
          attribute_conflict=按 resolved 值裁决（写入实体属性，留 apply_record）
         → reject：留档不执行
```

存储护栏：`graph_entities` 部分唯一索引 `(kb_id, name) WHERE merged_into IS NULL`（迁移内先确定性合并历史同名行：保留最早 created_at，重指关系后置 merged_into）；手动建实体「同名即链接」（并别名+freq+1 返回既有实体）。

## 4. Neo4j 投影（阶段 4）

- compose `neo4j` 服务（neo4j:5-community，heap 256m/max 512m/pagecache 256m 防 WSL 内存挤爆，仅内网不暴露宿主端口，卷 neo4j-data）
- backend/worker 共享 env：`NEO4J_URI/NEO4J_USER/NEO4J_PASSWORD`（缺省时投影自动禁用，服务不炸）
- 挂点：抽取落库/融合 accept/手动合并后 `resync_kb` 全量重建；实体/关系 CRUD 增量 upsert/delete（尽力而为）
- 查询：`shortest_path`（shortestPath ≤6 跳）、`neighbors`（1/2 跳）、`related_topk`（按权重）；**降级路径**：available()=False → 同名 `_pg` 后缀函数（PG 逐跳扩边/回溯 BFS）
- 认知契约：**PG 是唯一事务真源**，Neo4j 是可重建的查询镜像——任何不一致都能用「重建投影」收敛

## 5. 知识应用（阶段 5）

- API：`GET /graph/query/path|neighbors`、`GET /graph/entities/{id}`（详情+关联）、`POST /graph/resync`、`GET /graph/neo4j/status`
- 图问答：KB 对话（`/bases/{id}/chat`）与 RAG（`/bases/{id}/query`）在提示词注入 `【知识图谱三元组】` 块——问题命中实体名/别名（≤5）→ 1 跳三元组（≤30 条带证据），无命中静默跳过
- 前端（components/kg/）：`ExtractionControl`（快速/深度双按钮+进度轮询+取消）、`OntologyModal`（按库词表编辑）、`FusionPanel`（待审队列：合并确认/属性冲突裁决）、`EntityDetailDrawer`（属性表/别名/来源徽标/关联实体定位）、`PathQueryModal`（起点终点→路径面包屑，节点可点定位）

## 6. 已知限界与后续

- 深度抽取成本：120 chunk/次护栏，超出部分靠断点续抽分批；全网库（2,312 chunks）完整抽取需分批跑多次
- 融合 Pass3 的 LLM 仲裁复用对话档案（purpose=kg_fusion，仅审计分类用，不按 purpose 选模型）
- Neo4j 投影是查询优化而非功能依赖：graph 页总览/列表/抽取始终走 PG，删 neo4j 容器功能不缺只慢
- 存量库要获得领域类型需重跑深度抽取（auto/llm 双层并存，规则层结果不受影响）
