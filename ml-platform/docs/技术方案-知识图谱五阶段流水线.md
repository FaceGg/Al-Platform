# 技术方案：知识图谱五阶段流水线（LLM 抽取 + Neo4j 投影 + 融合审核 + 图应用）

> 2026-11-20 立项，当日交付。背景与用户决策链见 DEVELOPMENT_PLAN.md 2026-11-20 条目。
> 技术路线为用户四项拍板：**LLM 抽取 / 引入 Neo4j / 自动融合+人工审核 / 五阶段一次到位**。

## 0. 决策记录

| 决策点 | 选择 | 关键理由 |
|---|---|---|
| NER/RE 引擎 | LLM 抽取（平台 LLM 网关） | 零新基建、领域语义类型（对比 jieba 词性桶）；BiLSTM-CRF/BERT 需 BIO 标注数据+transformers 全栈（探查结论最低 2-4 周） |
| 三元组存储 | Neo4j 投影镜像 + PG 事务主源 | PG 已验证 7,915 实体/67 万边规模；投影幂等（MERGE by entityId）避免双写一致性黑洞；Neo4j 承担多跳/路径/关联查询 |
| 知识融合 | 确定性归并自动执行 + 模糊/冲突进人工审核 | 同名/别名归并证据充分可自动；语义对齐与属性冲突裁决需人担责 |
| 旧规则引擎 | 保留为「快速抽取」通道 | method="rules"/"llm" 双层并存，重建互不影响（**2026-11-24 修订作废**：两层不再并存，见下一行与 §7） |
| 抽取结果的关系（2026-11-24 修订） | **快速抽取与深度抽取不并存，以最后一次抽取为主** | 用户指示；一个库只有一份抽取结果，「状态标注」与「画布标题栏」是同一组数字，不再需要「全图 / 抽取结果」两套口径（§7） |

## 1. 五阶段映射

| 阶段 | 实现 | 状态 |
|---|---|---|
| ① 数据获取与预处理 | kb_documents 上传解析（PDF/docx/xlsx/文本）+ `_pack_chunks` ~600 字符分块；LLM 抽取以 chunk 为单元 | 复用既有 |
| ② 知识抽取 | `knowledge_graph_llm_extraction.py`：按库本体约束 → 分片调网关 → 契约校验+单轮修复 → 聚合落库；实体带别名/属性/关系证据；规则引擎并行保留 | 新增 |

## 2. 抽取引擎（阶段 2）

> 2026-11-24 修订：本节「落库语义」一条已被取代——抽取结果为流式构建且快速/深度两层不再并存，现行语义见 §7.1。其余条目（契约、修复回路、提示词、任务化、断点续抽）继续有效。

- **契约**：`KgUnitExtraction`（entities[{name,type,aliases,attributes[{name,value,evidence}]}], relations[{source,target,type,evidence}]），pydantic 校验 + `parse_llm_json` 容忍围栏/截取
- **修复回路**：契约失败 → 坏输出+校验错误喂回重试一次 → 仍败则 raw_first/raw_retry 各截 1500 字符留档进单元结果 `error`
- **提示词**：S1 范式——输出骨架逐字示例 + 类型词表 + 条数上限（实体≤20/关系≤15）+ chunk 文本引述块隔离 + 显式 max_tokens（`kg_llm_max_tokens`=3000，勿吃 2000 缺省）
- **任务化**：`kg_extraction_jobs` + celery `ml_platform.execute_kg_extract`（broker 不可用降级进程内线程）；逐 chunk 落 `kg_unit_results`（幂等键 kb_id+chunk_id+content_hash）→ **断点续抽**：重跑跳过已成功单元；取消标记逐单元检查；`kg_llm_max_chunks`=120 成本护栏；`kg_llm_time_budget_seconds`=1800
- **落库语义**：聚合全部 ok 单元 → 清 `method="llm"` 层 → 实体链接（与 manual/rules 存活实体归一化同名/别名命中时复用 id 不新建）→ 批量插入；类型/关系词表强制 coerce 到本体（兜底「概念/相关」）
- **规则层同批升级**：`_clear_auto_layer` 按 method 清层；规则抽取同样接入实体链接复用（`kg_names.existing_entity_index`）；`_normalize_name` 委托 `kg_names.normalize_name`（ASCII 词含大写 casefold，两层一套归一）

## 3. 知识融合（阶段 3）

```
抽取完成 → Pass1 同名/别名归并（自动，accepted 留痕）
         → Pass2 属性冲突（同实体同属性跨文档异值 → pending）
         → Pass3 difflib≥kg_fusion_fuzzy_threshold(0.92) 候选对
                → LLM 批量仲裁（same/canonical/reason；LLM 不可用→全部进人工队列）
                → pending 合并建议
人工审核 → accept：merge_entity=重指关系→(winner,loser,type) 去重保留最高权重
                → loser 原名与别名并入 winner.aliases → 属性并集
                → loser.merged_into=winner（存活过滤处处生效）
          attribute_conflict=按 resolved 值裁决（写入实体属性，留 apply_record）
         → reject：留档不执行
```

存储护栏：`graph_entities` 部分唯一索引 `(kb_id, name) WHERE merged_into IS NULL`（迁移内先确定性合并历史同名行：保留最早 created_at，重指关系后置 merged_into）；手动建实体「同名即链接」（并别名+freq+1 返回既有实体）。

## 4. Neo4j 投影（阶段 4）

- compose `neo4j` 服务（neo4j:5-community，heap 256m/max 512m/pagecache 256m 防 WSL 内存挤爆，仅内网不暴露宿主端口，卷 neo4j-data）
- backend/worker 共享 env：`NEO4J_URI/NEO4J_USER/NEO4J_PASSWORD`（缺省时投影自动禁用，服务不炸）
- 挂点：抽取落库/融合 accept/手动合并后 `resync_kb` 全量重建；实体/关系 CRUD 增量 upsert/delete（尽力而为）
- 查询：`shortest_path`（shortestPath ≤6 跳）、`neighbors`（1/2 跳）、`related_topk`（按权重）；**降级路径**：available()=False → 同名 `_pg` 后缀函数（PG 逐跳扩边/回溯 BFS）
- 认知契约：**PG 是唯一事务真源**，Neo4j 是可重建的查询镜像——任何不一致都能用「重建投影」收敛

## 5. 知识应用（阶段 5）

- API：`GET /graph/query/path|neighbors`、`GET /graph/entities/{id}`（详情+关联）、`POST /graph/resync`、`GET /graph/neo4j/status`
- 图问答：KB 对话（`/bases/{id}/chat`）与 RAG（`/bases/{id}/query`）在提示词注入 `【知识图谱三元组】` 块——问题命中实体名/别名（≤5）→ 1 跳三元组（≤30 条带证据），无命中静默跳过
- 前端（components/kg/）：`ExtractionControl`（快速/深度双按钮+进度轮询+取消）、`OntologyModal`（按库词表编辑）、`FusionPanel`（待审队列：合并确认/属性冲突裁决）、`EntityDetailDrawer`（属性表/别名/来源徽标/关联实体定位）、`PathQueryModal`（起点终点→路径面包屑，节点可点定位）

## 6. 已知限界与后续

- 深度抽取成本：120 chunk/次护栏，超出部分靠断点续抽分批；全网库（2,312 chunks）完整抽取需分批跑多次
- 融合 Pass3 的 LLM 仲裁复用对话档案（purpose=kg_fusion，仅审计分类用，不按 purpose 选模型）
- Neo4j 投影是查询优化而非功能依赖：graph 页总览/列表/抽取始终走 PG，删 neo4j 容器功能不缺只慢
- 存量库要获得领域类型需重跑深度抽取（auto/llm 双层并存，规则层结果不受影响）（**2026-11-24 修订**：两层不再并存——改用深度抽取会替换快速抽取结果，见 §7.1）

## 7. 2026-11-24 修订：抽取结果不并存 + 重新抽取并入主按钮 + 看门狗/状态修复

> 起因：用户三项反馈——①重新抽取后状态标注「实体 25 · 关系 24」与画布标题「实体 405 / 视图 100」对不上；②「重新抽取」应并入快速/深度抽取按钮，已抽取过的先弹确认框；③工具栏布局。实施中用户追加指示：**快速抽取与深度抽取不应并存，以最后一次抽取的为主**。本节取代 §2「落库语义」与 §0 原「双层并存」决策；§5 前端组件清单中的 `ExtractionControl` 已拆为 `useKgExtraction` / `ExtractionActions` / `ExtractionStatus`。

### 7.1 数据模型：一个库只有一份抽取结果

- `current_layer(db, kb_id)`：按库存活抽取实体（`properties.source="auto"`）的 `method` 判定当前图谱来源——`rules` / `llm` / `mixed`（两层并存时期的存量库）/ `None`（未抽取）。
- `clear_extraction_results(db, kb_id)`：清空两种抽取结果（各走 `_clear_auto_layer`，再删两端都落在手工实体上的抽取关系），手工行保留，不提交事务。
- 快速抽取（`POST /graph/extract`，`mode=rules`）：先清空上一轮结果再重建；**保留大模型分片缓存**。同库有进行中的深度抽取任务时 409——否则任务后续分片会写回刚重建的结果，两种结果重新混杂。
- 深度抽取任务启动：`rebuild = force or current_layer != "llm"`。图谱不是纯深度抽取结果就整体清空重建；已是深度抽取结果则在原结果上续建（断点续抽 / 新增文档），已有产出不动。重建时抽过的分片按 `kg_unit_results` 缓存回放（不调大模型），回放片计入进度。
- `kg_unit_results` 的语义 = **每个分片最近一次大模型抽取的结果**（不再是图的镜像）：`force`（全部重新抽取）启动时作废缓存；`pending_chunks` = 没抽过的分片数，`cached_chunks` = 抽过的分片数。
- `properties.job_id` 标签与 `GET /graph/extract/jobs/{job_id}/graph` 端点退役：任务计数与画布统一为**库内图谱规模**（存活实体数 / 端点都存活的关系数：任务内用 `graph_ids` 的 id 集增量维护，接口用 `graph_totals` 子查询计数）。
- 实体链接只会复用到手工实体（快速抽取结果已在任务启动时清空），复用时类型保持原样。

### 7.2 接口

- `GET /bases/{kb_id}/graph/extract/summary` → `{chunks, current, graph:{entities,relations}, rules:{extracted,entities}, llm:{extracted, pending_chunks, cached_chunks, latest_job, active_job}}`。`rules.extracted` 与 `llm.extracted` 至多一个为真（「当前图谱是谁生成的」，不是「历史上跑没跑过」）。「最近任务」按 `coalesce(started_at, created_at)` 倒序——创建时间只有秒级精度，中断后立刻续抽的两个任务会同秒创建。
- `GET /bases/{kb_id}/graph` 不变；画布只有这一份数据源。

### 7.3 前端

| 点击 | 条件 | 行为 |
|---|---|---|
| 快速抽取 | 未抽取 | 直接执行 |
| 快速抽取 | 当前图谱由快速抽取生成 | 确认「重新抽取」 |
| 快速抽取 | 当前图谱由深度抽取生成（或混杂） | 确认「改用快速抽取」：提示将替换现有图谱 |
| 深度抽取 | 未抽取 | 直接执行 |
| 深度抽取 | 当前为深度抽取、有待抽分片 | 确认「抽取未完成的 N 片」；次要动作「全部重新抽取」 |
| 深度抽取 | 当前为深度抽取、无待抽分片 | 确认「重新抽取」（force） |
| 深度抽取 | 当前为深度抽取、无待抽分片，但上次任务没成功结束 | 确认「重试」：只重做归并与同步，不调用大模型；次要动作「全部重新抽取」 |
| 深度抽取 | 当前为快速抽取（或混杂） | 确认「改用深度抽取」：说明多少片按缓存恢复、多少片调大模型；有缓存时次要动作「全部重新抽取」 |

- 状态行：两种抽取至多一个标「当前图谱 · 实体 N · 关系 M」，另一个「未抽取」；存量混杂库两者都标「快速+深度混杂」（悬停说明）。任务进行中显示进度（片数 + 实体/关系）；深度抽取任务一启动，快速抽取就不再标「当前图谱」。
- 任务没成功结束（收尾的归并/同步失败、最后一刻取消）时，状态行给续建入口：有待抽分片是「继续抽取」，分片都抽过了是「重试」——续建任务不调用大模型，只重做收尾。
- 手工增删实体/关系、融合审核、手动刷新之后，图谱与抽取摘要一起重新拉取（`reloadGraph`），标注跟着图谱规模走；标注与标题栏的数字统一千分位。
- 画布标题栏「实体 N · 关系 M」：任务进行中取任务行计数（与进度文字同源），其余取画布数据——与状态标注逐项相等。
- 画布：`ReactECharts` 改合并模式（`notMerge=false`，key 只随库变）——力导向按节点 id 记住坐标，抽取期间新节点长进现有布局而不是整图重排；「重置视图」走 `restore` 重建系列、从头布局。抽取期间的图谱刷新走 `loadGraph({quiet:true})`（不转圈、不清选中，4 秒节流）。
- 摘要还没加载完（或上次加载失败）时点按钮：先补拉摘要，再决定走哪条确认流程。
- 工具栏两行：第 1 行左搜索、右 [快速抽取][深度抽取][路径查询][隐藏文字]；第 2 行两类抽取的状态。图谱规模、当前视图、视图上限、重置视图移入画布卡片标题栏。

### 7.4 同批修复的缺陷

| 缺陷 | 现象 | 修复 |
|---|---|---|
| 看门狗阈值三元表达式写反 | 非流式通道拿到 150s（单次调用合法上限 240s），慢但正常的分片被判卡死，任务 3/18 片提前结束 | 非流式 300s / 流式 150s（与台账 2026-11-23 记录的口径一致） |
| 提前结束的任务被标「已完成」 | 3/18 片就结束，界面显示绿色完成标注，剩余分片无人续抽 | 主批次没跑完 → `failed` + `interrupted before finishing`；一个分片都没抽出来 → `failed` |
| 强制重抽中断后缓存未作废 | 图里只剩 3/18 片，界面显示待抽 0 片、没有「继续抽取」入口 | `force` 启动时作废分片缓存 |
| Neo4j 投影无索引 | 投影按 `(kbId, id)` 定位节点却没有任何索引，每条关系的两次 MATCH 都是全标签扫描：399 实体 / 6,230 关系全量重建 30 秒；同步的快速抽取请求 31 秒，超过前端 30 秒超时——后端做完而页面不刷新 | 首次连上时幂等建 `KGEntity.id` 唯一约束 + `kbId` 索引（存量部署自动生效）；实测重建 30 秒 → 0.7 秒 |
| 融合归并对「本轮已合并的对」抛异常 | 候选索引是本轮开始时的快照：互为别名的一对，反方向再合并时走进防环分支抛 `ValueError`，整个抽取任务被判失败。缓存回放建的图所有实体同一秒创建，稳定触发（流式抽取按分片先后创建，多数时候避开） | 先把对方解析到最终存活者（`resolve_merged`），已并入当前实体的直接跳过 |
| 「最近任务」同秒排序不确定 | 创建时间只有秒级精度，中断后立刻续抽的两个任务会同秒创建，谁排前面不确定 | 按 `coalesce(started_at, created_at)` 倒序 |
| 手工改动后标注不刷新 | 增删实体后标题栏即时变化，标注停在旧数字 | 手工改动后图谱与摘要一起重新拉取 |

### 7.5 存量数据

两层并存时期的库在下一次抽取之前保持混杂（摘要 `current="mixed"` 如实报告）；之后的第一次抽取——无论哪一种——整体重建。
