## 2. 第一批实施排期（13 项 · 5 阶段）

> 排序依据路线文档「模块间依赖主线」：数据侧（B1-08）、事件侧（B1-07→05→01→02）、模型侧（B1-09）、治理侧贯穿。F1 三线互相独立可并行；F3 三项**共用同一聚合视图**，必须同阶段做以保证 KPI 与列表口径严格一致（竞品趋势页与日报数字打架是反面教材）。

### F1 · 基座（B1-10 场景与设备管理 / B1-08 外部库直连 / B1-11 通知渠道）

- **为什么先做**：B1-10 的字段角色与设备台账被 B1-02（波形列把关）、B1-05（心跳/离线）、B1-07（场景 schema）引用；B1-11 是 B1-01 SLA 通知与漂移严重级推送的通道底座；B1-08 是数据侧源头。
- **交付物**：三张新表族（场景配置/设备台账含心跳、数据源连接（Fernet 加密）、通知渠道扩展）+ 各自 API + 前端管理页 + 迁移。
- **阶段验收**：新场景→字段角色→训练特征排除全链；设备注册→心跳→离线状态；白名单外 SQL 拒绝落审计；钉钉/短信测试消息可达且 secret 不回显。
- **B1-10 同时预留**：设备影子 desired/reported 状态字段（诚实设计⑤）。
- 〔更正 C1〕**通知通道现状**：平台已有站内信、企业微信群机器人、邮件、通用 Webhook 四通道——B1-11 实际只补钉钉（HMAC 加签）与短信两个通道，外加每通道「发送测试消息」按钮；凭据加密模块已有，掩码回显口径在详设时核对即可。
- 〔增补 E27〕**规格定义单一来源**（B1-10）：规格统一为「字段 + 波形统计量（值/均值/最小/最大/RMS）+ 上下限 + 单位」——本平台有波形列，这一结构可直接对波形统计量设规格；B1-02 判据引擎与 B1-06 能力指数都读它。路线文档在 B1-10「参数单位与上下限」、B1-02「规格上下限」、B1-06「USL/LSL」三处各说各的，不统一必然口径分叉。
- 〔增补 E17〕**Fernet 主密钥轮换脚本**（B1-08/B1-11）：通知凭据、LLM 档案凭据各自有 Fernet 主密钥，全仓没有轮换能力；本阶段新增加密字段时同批补上重加密工具。
- 〔已立项 E19〕**轻量部署 profile**（独立小批，可与 F1 三线并行）：先建 compose profile 机制，再出轻量 profile（关停 MLflow、Neo4j、TensorBoard 网关、标注端等非核心服务并设资源限制）；**默认栈保持现状不变**；安装包与升级脚本同批验证。B1-07 的 Kafka profile 在 F5 复用同一机制。
- 〔已立项 E23〕**帮助中心骨架**：顶栏全局「帮助」入口 + 章节结构 + 全局搜索，先把现有操作手册结构化导入；之后每个新页面与其帮助页同批交付（§6-11）。

### F2 · 预警处置主干（B1-01 预警中心 → B1-02 处置工作台 → B1-12 证据链导出）

- **顺序硬依赖**：B1-02 从 B1-01 点入；B1-12 打包 B1-01/02 产生的轨迹与判据。
- **内部分两波**（增补后本阶段最重）：**F2a** = B1-01 → B1-02，在 M1 关键路径上；**F2b** = B1-12，与 F3/F4 无依赖，可并行。
- **交付物**：alerts 表 + alert_events 轨迹表 + 误报回流标注队列挂接（复用 annotation_strategies）+ 判据优先级引擎（规格超限→3σ→2σ→基线偏离 30%，竞品口径可复算）+ MinIO 附件 + ZIP/MANIFEST.SHA256 导出 + 预警中心与处置工作台前端页。
- **阶段验收**：路线文档 B1-01/02/12 三节验收口径逐条过；**确认动作强制责任人**（防呆优于竞品）；异机解包 SHA-256 校验通过。
- **通知联动**：SLA 临期/超时接 F1 通知中心。
- 〔增补 E20〕**预警同因合并**（B1-01）：按场景 + 设备 + 工位 + 时间窗 + 来源类型折叠成组、组内可展开。Kafka 接入后单条推理一个事件，没有合并预警中心不可用。
- **对标反面教材——触发下限独立于分级阈值**（B1-01）：预警**触发阈值**单独可配，不以「高 0.85 / 严重 0.95」分级阈值代替，并以诚实设计②脚注写明风险分口径。竞品 47.5% 置信度即发「强飞溅」预警在其矛盾清单里——只抄分级阈值会把这个坑一起抄进来。
- 〔增补 E07〕**SOP 版本化 + 处置单快照**（B1-02）：SOP 按编号、适用工况、生效时间版本化，含规格越限/SPC 越限/AI 风险三类处置指引；每张处置单记录**当时生效的** SOP 版本、SPC 基线版本、模型版本——审厂时「当时依据的是什么」可复现。
- 〔增补 E08〕**SPC 基线冻结前移到 F2a**：选已结束的稳定时段冻结基线（均值 + 平均移动极差/1.128，即 I-MR 口径），版本化并记录引用的事件序号。它本是 B1-06 的一部分，提前到 F2a 是因为上一条的处置单快照要引用基线版本；F4 再做完整控制图与能力指数。
- 〔增补 E21〕**闭环证据总览**（B1-12，F2b）：按模型版本查看 12 环节的完成/待发生/缺失状态，各步可打开依据串到数据集、切分、标注、训练轮次、模型、推理与反馈记录；上线检查五项（模型文件、校验和、数据版本、评估完整性、生产版本唯一）。第一批先接已有证据的环节，第二批的盲测、门禁、影子、回执环节在 S2b 接入。它是后面所有证据的聚合入口——缺了它，证据都是散的。

### F3 · 监控驾驶（B1-03 驾驶舱 / B1-04 趋势帕累托 / B1-05 实时监控）

- **同阶段强约束**：三页共用**同一 SQL 聚合视图**（alerts + 推理结果），单测锁「KPI 数字 = 下钻列表数字 = 趋势页计数」；NG 词表配置与后续 B3-08 质量报告共用一份。
- **交付物**：聚合视图 + 四级范围（工厂→车间→产线→场景）联动切换 + SSE/WebSocket 推送（复用闭环事件流，5 秒上屏）+ 设备三级树（读 F1 台账）+ 陈旧数据横幅（距最后推理 >24h）。
- **阶段验收**：模拟事件 5 秒内上屏；口径一致性单测；四级切换全卡联动；设备离线状态准确反映心跳。
- 〔增补 E09〕**处置运营三指标**（B1-03）：每千件处置单数、首次处理均时、结案率。竞品 14 条预警全部超时无人认领却无人察觉，正因为它没有处置效率指标。
- 〔增补 E22〕**演示数据隔离**（诚实设计第⑥项）：演示循环产生的样本、预警、KPI 全链带演示标记，不计入真实 KPI、不进标注真值与训练，全站有常驻演示态标识。先核对现有演示循环的隔离与标识，缺什么补什么。

### F4 · 统计与漂移（B1-06 SPC / B1-09 漂移页）

- **两项独立可并行**；均不含对 F2/F3 的硬依赖，但漂移报告的「一键转重训提案」在第一批只做到提案生成（审批流在第二批 S1）。基线冻结已在 F2a 落地（E08）。
- **交付物**：SPC 纯函数统计库（Nelson 1–8 判异 + Cp/Cpk/Pp/Ppk/Cpm/Cr/σ/PPM 全套，8 类判异单测全覆盖）+ 控制图/直方图前端；drift_reports 表族 + 定时批检 beat 任务 + 口径脚注（诚实设计②）。
- **阶段验收**：竞品同口径数据复算一致（106,504 行取最新 5,000、5 样本/组用例作为回归）；缺规格限能力指数留空不报错；定时批检真实产出分级报告且严重级推送通知。
- 〔更正 C2〕**漂移检测是新实现**：现有 PSI 是**分数级**（回流异常分数对训练期分位表做 10 等概率箱比较，只服务无监督部署的重拟合触发），竞品是**特征级**（39/89 特征漂移）。路线文档「不重写算法、只重组报告与页面」不成立——特征级 PSI、PCA 重构误差、DQ 检查三项都要新写。现有分数级 PSI 原样保留为触发器，并作为报告里的第四类信号挂入。

### F5 · 接入开放（B1-07 Kafka / B1-13 QMS/MES 只读接口）

- **B1-07 依赖 F1 的场景 schema 声明**；compose 可选 profile 不加重默认栈；按业务样本 ID 幂等去重；全站页脚实时链路状态（诚实设计⑤变体）。
- **B1-13 相对独立**：platform_api 反向改造为业务数据只读开放（九类 GET 资源、API Key 掩码+轮换宽限期、单页 500 上限）。
- **阶段验收**：端到端延迟秒级、重放不重复计数；外部脚本持 Key 分页拉取、轮换后旧 Key 401、写动词全 405。
- 〔更正 C5〕**profile 机制不在这里首建**：`docker-compose.yml` 现无任何 profile，17 个服务默认全启；机制已随 E19 在 F1 期间落地，本阶段只新增 kafka profile，且同样不得改变默认栈，验收栈与 e2e 同批验证。
- 〔增补 E18〕**事件接入契约**（B1-07）：版本化输入契约（来源、工位、业务事件 ID、采集时间、载荷版本、关键字段与单位）；同键不同内容可追查；记录重放位置；乱序与延迟标签可处理。
- **M1 收口**：第一批真实数据端到端演练（建议用三端标注运营的真实流量触发一条预警走到关闭），验收证据 `验收-补齐路线-M1.md/json`，全量 CI 全 job 全绿。

## 3. 第二批实施排期（14 项 · S0–S4，S2 分 a/b）

> 启动门控：第一批 M1 达成。治理四件套（B2-G1~G4）全部来自工序平台已演练机制，照抄不改语义。S1 与 S2a 互不依赖可并行；S3 独占窗口（见下）。

### S0 · 前置核查（B2-T）——已收口，无需立项

- **结论**：无监督异常检测建模出口**已存在**，B2-T 关闭，第二批仍为 14 项，不增项。代码证据（2026-11-19 内容级复核）：`backend/app/services/automl_anomaly.py`（IsolationForest/OneClassSVM 统一分数口径）+ `automl_anomaly_ae.py`（AutoEncoder），2026-11-12/13 全量方案已交付，按族混合形态。
- 路线文档 B2-T 提到的「异常排名稳定度作为无标签搜索比较准则」**同样已有实现**：`automl_anomaly.py` 的 `stability_check`、`rank_candidates`（stability 为第三排序键）、冠军资格门禁（含 stability 指标）三处。无残留核查项。

### S1 · 审批与审计底座（B2-07 统一四眼审批中心含 B2-10 / B2-08 动作审计）

- **为什么先做**：B2-03 门禁、G2 预授权、重训提案、配方变更全部汇入审批队列；B2-08 贯穿本批所有 LLM/Agent 调用。
- **交付物**：统一审批队列（类型字段 + 有效期默认 72h + 过期自动回收 + 过期前 12h 提醒）；发起人≠审批人强制、拒绝必附意见、批准后平台执行回写留痕；动作审计表（请求/结果/权限/耗时/审批关联/追踪 ID）+ 键名脱敏 + CSV 导出。
- **阶段验收**：审批人=发起人被拒；72h 过期自动回收实测；脱敏规则单测；此后本批每次 LLM 调用自动入审计。
- 〔更正 C4〕**审批状态四处并存**：AgentTask 审查状态、模型版本审批状态、模型卡审批状态与历史、技能修订审批；且项目角色（owner/editor/operator/viewer）里没有独立审批人。S1 的实质是「收敛存量 + 定义审批权限」，不是把 AgentTask 审批流简单泛化。详设第一步是存量收敛清单与迁移映射，不另建第五套状态机。
- 〔更正 C7〕**脱敏不另造**：`services/audit.py` 已有键名脱敏与变更脱敏，B2-08 复用。
- 〔增补 E06〕**审批单绑定内容指纹**：候选包摘要、目标范围、验收标准版本构成指纹——换模型、换工位、证据过期后旧审批自动失效，堵住「批的是 A、发的是 B」。
- 〔增补 E05〕**拒绝水位线**：拒绝重训提案时记录当时的新增样本数，新增样本超过水位线才再次自动提案，避免同一提案反复打扰审批人。
- 〔增补 E10〕**审计事件哈希链**：审计事件带前序哈希，提供完整性校验端点（返回是否完整、校验条数、首个断点）。审厂证据防篡改；随 B2-08 同批迁移，避免动两次审计表。
- 〔增补 E01 豁免部分〕**豁免走审批**：豁免请求进统一审批队列，理由不少于 10 字，豁免人≠发起人。

### S2a · 划分与盲测地基（B2-G1 独立终验 + 盲测样本锁定）

- **为什么独立成段**：〔更正 C3〕平台**没有数据集划分管理**——`services/automl_search.py` 两处硬编码 `train_test_split(test_size=0.2, random_state=42, stratify=…)`，接口模型无划分字段，前端无划分控件。路线文档「复用划分管理、加轮次锁定与盲测台账」的前提不存在，B2-G1 要先建划分管理本身，且改动触及 AutoML 训练核心路径。
- **交付物**：划分管理（策略可配、划分持久化、划分指纹）+ 轮次锁定 + 盲测台账（已用样本进历史证据，新轮次必须新批次）+ 盲测复核队列隐藏模型分数。
- **阶段验收**：路线文档 B2-G1 验收口径逐条过——轮次启动后划分不可变且落审计；盲测样本被使用后自动进历史台账；新轮次无法复用旧盲测。AutoML 全量回归通过，既有任务结果可复现。
- 〔增补 E04〕**入库即定、永不重分**：样本入库时一次分好归属，之后追加新批次不改旧样本归属；每批划分种子由（种子，批次序号）派生。
- 〔增补 E03〕**每轮盲测评估次数上限**（默认 2）：盲测锁定的配套——没有次数上限，「在盲测集上试到过为止」同样会泄漏盲测集。
- **兼容红线**：默认行为保持现状（20% 随机分层、seed 42），新能力以显式配置启用。

### S2b · 发布治理链（B2-09 → B2-02 → B2-03 → B2-G2 → B2-G3）

- **链式顺序即依赖**：Champion/Challenger 别名路由（B2-09）→ 影子推理对照（B2-02，Challenger 即影子候选）→ 发布门禁（B2-03，终验指标**只能取自 S2a 锁定盲测**——直接堵竞品「F1 0.999 浅验证集放行」漏洞）→ 预授权层（B2-G2，授权检查中间件）→ 影子窗口 + 灰度 + 回执（B2-G3，rollout 金丝雀映射灰度段）。
- **交付物**：release_checks 表随发布单归档；preauthorizations 表（工位/验收标准版本/有效期/次数余额）；三段式发布状态机；模型注册表别名表。
- **阶段验收**：路线文档 G2/G3、B2-02/03/09 各节验收口径逐条过——重点：授权人=申请人创建被拒；无回执不放量；低 F1/漂移超阈/样本不足/无盲测指标四种情形均拦截。
- 〔更正 C8〕**新门禁挂在既有硬门禁体系上**：`agent/hard_gates.py` 已有不可放宽的硬门禁（绝对门槛 + Top-K 方差 + 泄漏列进重要性前十即否决）。泄漏、无盲测这类硬门禁**不可豁免**——工序的豁免也只允许「终验通过、仅不回退未过」这一种情形，两边口径一致。
- 〔增补 E01〕**不回退检查**（B2-03 第五项检查）：候选与现役冠军在**同一批盲测样本**上配对盲评（不能直接用冠军当时记录的指标，盲测集会随新批次增长）；点估计加容差，不用置信区间；严格模式下禁止新漏检。
- 〔增补 E02〕**Wilson 置信界门禁**（B2-03，可配开关）：比例型指标取下界与阈值比较，界面同显点估计与置信界。
- 〔增补 E14〕**影子报告防选择偏差**（B2-02）：保持随机抽检对照，防止只看模型挑出的事件；生成绑定模型包、部署目标、验收标准版本的不可变报告。
- 〔增补 E16〕**重训预授权**（B2-G2）：与发布预授权并列，事先确认数据来源、工况、预算、验收标准版本、有效期，可随时撤销。
- 〔增补 E12〕**回执与回滚细节**（B2-G3）：回执携带产物摘要校验；证据时效校验；灰度实际打分量达标才全量；灰度期错误越线自动回退；分别显示计划版本、实际生效版本、最后回执。
- 〔增补 E11〕**现场准入签收单模板**（B2-G3 交付物）：六类项目（工位与范围、数据与真值、现行检验、验收标准、容量、版本）+ 五方交接清单 + 七项现场操作记录。治理上产线前的交付物，纯文档资产。
- **回执来源分层**（计划澄清）：路线文档 B2-G3 写「回执 = 工位侧打分服务确认新版本生效的记录」，但工位侧执行器在第四批（B4）才有——第二批落地时会卡在「没有工位」。分两层：**第二批先做服务端回执**（推理运行时按路由键——条件值路由已有——上报生效版本与实际打分量）；**第四批盒端回执接入同一回执契约**。回执契约（版本、产物摘要、打分量、时间窗）在 S2b 技术方案里一次定义。
- 〔增补 E13〕**验收场景矩阵以工序 C1–C18 为基线**：质量门、采纳、通知、数据不足、回退豁免、泄漏暂停、标签质量停止、无效回复切换特征、拒绝水位线、人工回写、一次启动、续跑、影子回放、发布回滚、回流迭代。其中本平台已有等价机制的（泄漏门禁、升级与修复回路）做映射说明，其余逐场景写端到端用例。

### S3 · 标注质量链（B2-05 主动学习选样 → B2-06 Kappa+仲裁 → B2-G4 伪标签凭证）

- **最大回归面在 B2-06**：单标注员指派制改「多人标注 + 仲裁」触及标注员门户核心流程，**独立排期窗口 + 完整回归**（简报明确此项为第二批最大回归面），不得与 S2 并行抢带宽。
- **交付物**：九策略选样（熵/Margin/最小置信度等不确定性族补齐，挂 annotation_strategies，初始预算+单轮预算）；Cohen's Kappa 计算 + 冲突仲裁队列 + 整簇纯度门禁（≥0.8 且规模≥10）+ 分群标注三类样本视图（群内代表/边界/偏离，工序借鉴 9，辅助整簇决策）；伪标签限量（每类按已标真值）+ 降权 + 开发验证比较选择器 + 凭证导出（红线：伪标签永不进终验）。
- **阶段验收**：九策略各有单测、混合按权重出样；冲突样本自动进仲裁、低纯度群无法整簇提交；超限量候选被拒、未胜出方案不被选用、凭证与库内一致。
- 〔增补 E15〕**标签质量治理**（B2-06）：标签质量门（疑似标签数量不足即停止并提示）；标签修订链（真值迟到或修正可追溯，只对后续版本生效，既有报告仍可复现）；样本用途标记（训练/影子/发布验证）。
- 〔增补 E25〕**分群自动选择**（B2-06 可选）：现有 `weighted_kmeans`、`umap_hdbscan` 两种方法，详设时评估是否加自动择优与 Khiops。

## 6. 横向工程合同（全批次统一纪律）

1. **批启动任务 = 技术方案先行**：每批开工第一个动作是 `ml-platform/docs/技术方案-补齐路线第N批.md`（批级一份、分章节按阶段追加详设），评审通过才动代码；阶段开工前把该阶段详设补入同一文档（2026-11-13 文档同步规约：文档与代码同批落、不留待办）。
2. **阶段验收 = 证据入 Git 跟踪目录**：`ml-platform/docs/验收-补齐路线-*.md` + 同名 `.json`；JSON 内区分 passed/failed/skipped/cancelled/not_run/环境阻塞，禁止 continue-on-error 折算成功。工序「每阶段回执 JSON + 日志 + 截图」的工程化做法可取，其证据放 gitignored 目录是反面教材——我方两者兼取，并补回执间的结构化比对。
3. **迁移纪律**：ORM 变更必须带 Alembic 迁移 + SQLite/PostgreSQL 双兼容 + 旧数据保留断言 + 保证单一迁移头；模型三件套必须进 `models/__init__` 导入链。迁移头常量已改为动态读取（r19 根治），无需手工同步。
4. **测试纪律**：新后端测试模块/新前端测试文件同批登记唯一周次（week_manifest）；新测试三件套同批提交；前端全量用例本地必跑（CI ubuntu 与本地 Windows 行为有差异，遗留 screen.debug 类语句用完即删）；**新增写接口纳入既有项目访问权限测试矩阵**（对标竞品「四角色 38/38 写接口冒烟拦截」）。
5. **前端惯例**：页面标题一律 PageHeading/V2PageFrame；时间解析必须 parseBackendTime；字体自托管（禁 CDN/专有字体）；组件勿用 export {} 列表。
6. **CI 与推送**：推送成功即完成批次汇报（CI 后台监视、结论下批顺带登记）；门禁收敛时 push 前必核 HEAD == 门禁验证过的 head_sha；共享工作树 commit 前必核 branch。
7. **安全扫描预注册**：本路线大量新增含 `def execute(` / `pd.DataFrame(` 的算子与服务文件，Mimosa 误报封锁概率高——新算子文件预注册覆盖绕行；外部输入一律参数化查询（B1-08/B2-01 的 SQL 白名单引擎是唯一例外面，需专门评审）。
8. **对标复算用例即回归用例**：路线文档中所有「竞品实测口径」（SPC 106,504 行取最新 5,000 复算、判据优先级链、PSI 严重 0.25 分级阈值、Cp 组内/Ppk 整体标准差口径）进单测锁死，防口径漂移。
9. **演示数据隔离**：所有新聚合视图（KPI、趋势、报告、证据包）默认排除演示数据。
10. **口径单一来源**：规格定义、NG 词表、冻结基线、盲测集各只在一处定义，其余模块引用。
11. **页面与帮助同批交付**：每个新页面落地时同批提交它的帮助页（帮助中心 E23），不积文档债。
12. **导航归属**：新页面按 §10 归属表落位；菜单项随功能交付出现，不预先挂空壳入口（竞品 31 个页面里一堆空态是反面教材）；新增菜单项同步 §10.3 列的骨架点。

## 10. 导航信息架构归属（2026-11-24 建议，待确认）

### 10.1 结论

**新增一个一级板块「质量管理」，其余全部并入现有五类，不新增第二个板块。**

- **不新增不行**：路线里 16 个页面（质量日常 6 个 + 第三批质量体系 10 个）是面向质量部门用户的业务功能。硬塞进「算法平台」，侧栏会从 10 项涨到 26 项，而且「算法平台」这个词盖不住 NCR、8D、供应商 SCAR；「首页门户」按设计没有侧栏，承载不了功能页导航。
- **只新增一个够用**：其余项要么是既有页面的深化（放进页内页签或详情页），要么数量撑不起一个板块——模型治理拆出来只有 2–3 个独立菜单项，边缘只有一组。
- **审批中心与帮助中心做成顶栏全局入口，不占板块**。审批中心尤其不能放「系统管理」：该板块只有管理员可见，而审批的发起人包含所有角色。

依据（代码现状）：顶栏五个视图 + 侧栏分组菜单（`components/AppLayout.tsx`）；板块名唯一来源是 `components/PageHeading.tsx` 的 `SECTIONS`；除「系统管理」按管理员显隐外，其余菜单对所有登录用户全量可见；门户首页标题为「一个平台，三大中心：算法 · 智能体 · 基础设施」（`pages/PortalPage.tsx`）。

### 10.4 待决策

1. **板块名**：建议「质量管理」（英文 Quality Management），与现有板块命名同风格；若更强调日常运营，可叫「质量中心」。
2. **板块是否按角色显隐**：现状除系统管理外全部可见。新板块上线后所有用户都会多一个页签，质量部门用户同样会看到算法平台、智能体中心、基础设施。按角色配置可见板块需要扩展平台角色模型，与 S1 的审批人角色（§9.5 C4）是同一个问题，建议在第一批技术方案里一起设计。
3. **门户叙事**：新增板块意味着「三大中心」变「四大中心」，这是对外定位话术的变化。
