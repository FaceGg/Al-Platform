## 一、设计目标与原则

1. **大模型当数据科学家**：分析、决策、写特征代码、写评审结论；**数值计算一律平台工具**，
   LLM 只读工具产出的结构化报告做判断。
2. **通用场景，零内置域逻辑**：不预置"电焊算子/拧紧算子"。领域知识来自三处——
   列名语义（制造数据普遍带中文注解）、知识库（可随时上传新场景工艺文档）、配方库 few-shot。
   新增场景（SMT 贴片、CNC 加工、涂装、注塑、装配质检…）不需要改代码。
3. **自我纠错，没有兜底捷径**：LLM 产出的特征脚本错了就拿到真实报错自己改，
   改好才进下一步；改不动才升级人工（附完整尝试档案）。
4. **每个 LLM 输出都是可校验的结构化 JSON**（分析报告/特征脚本/评审结论三类契约），
   校验失败同样进入自我纠错循环。
5. **迭代有界 + 验收双门**：分析→特征→建模→评估默认最多 3 轮，脚本修复最多 8 次；
   硬门禁一票否决，LLM 只能建议、不能放宽。
6. **Skill 化交付**：流程、契约、工具说明、配方库打包成一个技能目录，
   配置 `llm_api_url/key/model` 即可运行；平台侧只需要一个薄的 Agent Runner。

## 二、总体架构

```
┌──────────────────────────── Agent Runner（薄编排器） ────────────────────────────┐
│  加载 skill 定义（SKILL.md + contracts + tools）                                  │
│  + 跨任务经验库检索（按域/画像相似度取 top-k 注入）                                │
│  while 轮次 <= 3 且未验收:                                                       │
│    S1 数据智能分析（域自动发现，注入：上轮全链记忆 + 相近任务经验条目）             │
│      → S2 特征工程：LLM 写脚本 ⇄ 沙箱执行 ⇄ 读真实报错自我修复（≤8 次，无兜底；    │
│             每次报错与修复动作结构化沉淀）                                         │
│      → S3 AutoML 搜索（平台现有引擎）                                            │
│      → S4 硬门禁 + LLM 评审（重要性 vs S1 预期对齐）                              │
│    fail → 失败原因入轮内记忆 → 回 S1；escalate/超限 → 人工（全档案随附）            │
│  验收通过 → 固化 Recipe（版本化）+ 任务经验蒸馏入经验库                            │
│           → 订阅回流重训 / 新数据 delta 复用                                      │
└──────────────────────────────────────────────────────────────────────────────┘
        ▲                                                              │
        └── 技能演进（有界 RSI，见第十章）：经验库定期提炼 SKILL.md 修订提案            │
            → 基准回归集离线验证 → 人工批准（按风险分级）→ 技能版本 +1（可回滚）        │
```

## 三、四个阶段的详细设计

### S1 数据智能分析（域自动发现）

**工具（确定性）**：`profile_data(dataset, target)` 产出——
- 每列：类型/缺失率/基数/分位数/常量列标记；列名与注解拆分（`ACTUAL_TORQUE(实际扭矩/一轴实际扭矩)`
  → 基础名 + 中文语义，制造数据的天然领域线索）；
- 目标列：类别分布、不平衡度、标签语义（"0-不合格，1-合格"）；
- 与目标列的互信息 Top-K、列间高相关对（>0.95）、时间列识别；
- 抽样行样例（≤20 行，脱敏后）供 LLM 直观理解。

**LLM 输入**：画像 JSON + 目标列语义 + 知识库检索（按列语义自动检索工艺/标准文档，可选）+
上一轮迭代记忆 + 配方库中相近场景的 few-shot（可选）。

**LLM 输出契约 `AnalysisReport`**（JSON Schema 强校验）：

```json
{
  "domain_hypothesis": "tightening",          // 自由推断：welding/smt/cnc/painting/...或新造
  "domain_reasoning": "列语义集中在扭矩/上下限/双轴/程序号 → 拧紧装配场景",
  "focus_channels": [
    {"name": "torque_deviation", "columns": ["ACTUAL_TORQUE", "TARGET_TORQUE"],
     "why": "实际与设定偏差是不合格主因"}
  ],
  "expected_important_features": [
    {"name_hint": "torque_lower_margin", "reason": "贴下限即欠拧", "priority": "high"}
  ],
  "data_quality_actions": [
    {"column": "ACTUAL_TORQUE_TWO", "issue": "单轴行整列缺失", "action": "impute+flag"}
  ],
  "leakage_suspects": [{"column": "DECIDE_ONE", "why": "与目标同源的中间判定"}],
  "class_balance_concern": "20.5% 不合格 → class_weight",
  "feature_engineering_brief": "派生偏差/带宽比/上下裕度/双轴差/缺失标记；剔除判定中间列"
}
```

验证样例的互证标准（不写死进代码，仅验收时人工核对）：电焊应聚焦电流/电压/电阻/功率通道
与飞溅/熔核；拧紧应聚焦扭矩偏差/裕度/双轴。S1 推断错域 = 天然进入 fail 循环自我修正。

### S2 特征工程：LLM 自我纠错循环（v0.2 核心，无内置回退）

```
loop 尝试 = 1..8:
  script = LLM(brief + 历史报错摘要 + 数据契约)      # 纯函数式 DataFrame→DataFrame
  result = sandbox_run(script, 抽样5k行)             # 平台沙箱：限时/限内存/禁网络/禁模型
  if 可执行且过校验: 进入 S3
  否则: 把【真实错误】喂回 LLM：
    - 语法/运行错误 → 完整栈回溯 + 出错行 + 输入 dtype 样例
    - 契约违规 → 具体规则（行数变了/输出全空列/含泄漏列/方差=0）
  同类错误重复 ≥3 次 → 注入 meta 提示："该方法不收敛，请换思路而非重复修补"
全部失败 → escalate（附 8 次脚本+报错档案），人工介入
```

- **没有内置算子兜底**——场景通用性的代价由 LLM 的修复能力承担；电焊/拧紧的现有实现
  （73 维/6 派生列）降级为**配方库中的参照范例**（few-shot 素材），不再是运行时回退路径。
- 校验分层：可执行 → 行数不变 → 无全空/常量输出列 → 无 leakage_suspects → 数值列方差 > 0。
- 每次定稿脚本与试运行指标落盘，成为配方资产与审计档案。

### S3 自动建模（现有 AutoML 零改动）

LLM 依画像微调搜索配置（不平衡→class_weight、小样本→缩 trials、疑时序漂移→时间切分 CV），
平台执行 optuna 贝叶斯 + 多算法族搜索，产出 Top-K 候选的 CV 指标 + `feature_importance`。

### S4 评审验收（硬门禁 + LLM 评审）

**硬门禁（确定性、一票否决、LLM 不可放宽）**：
- 留出测试集按**少数类**设阈：precision / recall / F1 / AUC ≥ 业务预设
 （拧紧样例：不合格召回 ≥ 0.90；电焊样例：fault 召回 ≥ 0.85）；
- Top-K 模型指标方差小（防偶然冠军）；重要性 Top10 无 leakage_suspects。

**LLM 评审 `ReviewVerdict`**：特征重要性与 S1 预期的逐项对齐、意外发现（如"ID 列排第 3，
疑似索引信号"）、业务就绪度叙述、`next_iteration_hints`。`fail` → 回 S1（hints 入记忆）；
`escalate`/超轮次 → 人工。

## 四、固化与复用：Pipeline Recipe

```json
{
  "recipe_version": "tightening-v1.0",
  "domain": "tightening",
  "inputs": {"target_column": "DECIDE(判定…)", "minimal_columns": ["ACTUAL_TORQUE", "..."]},
  "analysis_digest": "S1 报告摘要（delta 分析基准）",
  "feature_script": "<S2 定稿脚本>",
  "automl_config": {"families": [...], "trials": 30, "cv": "stratified_5", "class_weight": true},
  "acceptance_gates": {"minority_recall": 0.90, "f1": 0.85},
  "review_log": [...], "model_lineage": {...}
}
```

复用三条路：
1. **回流重训**：闭环报错积累 → 按配方直接执行（不唤醒 LLM），硬门禁失败才唤醒 Agent；
2. **新数据 delta**：新画像 vs `analysis_digest`，差异小直接跑，差异大进完整迭代；
3. **新场景迁移**：配方作为 few-shot 注入 S1（"拧紧配方"帮 LLM 理解"角度监控装配"新场景）。

## 五、Skill 化封装（最终交付形态）

平台新增技能目录（与文档同级的一等公民），配置大模型即可全自动：

```
ml-platform/skills/automl-agent/
├── SKILL.md            # 触发条件（"有数据集+目标列，需要建模"）+ 流程指令 +
│                       #   硬门禁铁律 + 自我纠错策略 + 输出规范 —— 即 LLM 的操作手册
├── contracts/          # AnalysisReport / FeatureScript / ReviewVerdict / Recipe 的 JSON Schema
├── tools.md            # 平台确定性工具清单与调用约定：
│                       #   profile_data / sandbox_run / train_automl / holdout_evaluate /
│                       #   persist_recipe / query_kb / search_recipes
└── recipes/            # 配方库（版本化，跨场景 few-shot 素材）
```

- **Agent Runner（平台侧唯一新增代码）**：读 SKILL.md 驱动循环、按 tools.md 调平台工具、
  对 LLM 输入输出做契约校验与记忆管理。LLM 配置复用现有 `llm_api_url/key/model`。
- **技能可演进**：改进提示词/门限/流程 = 改 SKILL.md（版本化），不动平台代码；
  也可衍生子技能（如"回归建模技能"复用同一 Runner）。

| 阶段 | 内容 | 交付判据 |
|---|---|---|

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 脚本修复不收敛（去掉兜底后最大风险） | 8 次上限 + 同类错误重复检测 + meta 换思路提示 + 升级人工全档案；配方库与经验库 few-shot 显著降低冷启动失败率 |
| LLM 幻觉/恶意脚本 | 结构化契约 + 沙箱（禁网络/禁模型/限时限内存）+ 泄漏复查；LLM 产物全部落盘审计 |
| 域误判（新场景） | S1 输出 domain_reasoning 可解释可人工复核；fail 循环天然纠错；知识库补文档即补域知识 |
| 评估过拟合 | 测试集只在 S4 出现一次；迭代选型用 CV |
| 不平衡学成全判多数 | 硬门禁按少数类召回设阈，LLM 不可放宽 |
| Token 成本 | 固化后走配方不唤醒 LLM；画像列级摘要压缩；delta 复用；经验注入仅取 top-k 相关条目 |
| 经验污染（错误教训被复用） | ExperienceEntry 带证据链（来源任务/指标/评审结论）；检索时带置信度；技能演进前必须过回归集；低置信条目只提示不自动生效 |
| RSI 失控 / 自我放宽标准 | 自我改进**只允许收紧不允许放宽**硬门禁与契约；运行中禁止热改技能；演进每周期一次且人工分级审批；全版本可回滚 |

## 十、跨轮经验系统与有界 RSI（v0.3 新增）

> 需求来源：每轮自动迭代都要利用好上一轮的经验和分析过程；并参考 RSI
> （Recursive Self-Improvement，递归自我改进）——让智能体不止在单任务内迭代，
> 还能把积累的经验反哺到自身技能上，越用越强，但改进必须可控可回滚。

### 10.1 三级经验体系

| 层级 | 生命周期 | 内容 | 注入方式 |
|---|---|---|---|
| L1 轮内记忆（Run Memory） | 单任务迭代内（≤3 轮） | 每轮四步产物摘要 + fail 原因 + hints + S2 的报错-修复对 | 下一轮 S1/S2 提示词固定携带（全量，任务小） |
| L2 跨任务经验库（Experience Store） | 永久，随任务增长 | 任务结束蒸馏出的**可泛化**教训条目 | 新任务启动时按 domain / 画像相似度检索 top-k 注入 S1 |
| L3 技能本体（SKILL.md） | 版本化，演进式 | 提示词、默认动作、纠错策略、门禁建议 | Agent Runner 加载即生效（改它 = 技能演进，见 10.3） |

### 10.2 L2 经验条目契约（ExperienceEntry）

```json
{
  "id": "exp-0042",
  "domain": "tightening",
  "situation": "索引/单基数码列（ID、程序号）被树模型高权重利用",
  "lesson": "索引类与单基数码列默认应剔除或频度编码，不应裸入模",
  "action": "S2 脚本默认 drop 单基数码列；S4 泄漏复查扩到 cardinality>0.9*n 的列",
  "evidence": {
    "source_tasks": ["task-0017", "task-0023"],
    "metrics_delta": "剔除后不合格召回 0.91→0.93",
    "review_refs": ["轮2 ReviewVerdict.surprises"]
  },
  "generality": "cross-domain",
  "confidence": 0.86,
  "status": "active | retired | superseded"
}
```

- **写入时机**：任务验收通过（成功经验）或升级人工后（教训同样有价值），
  由 LLM 从全链路档案蒸馏，契约校验后入库；带完整证据链，杜绝无依据"格言"。
- **检索**：新任务 S1 时按 `domain` 匹配 + 画像向量相似度取 top-k（默认 5 条），
  仅注入 `confidence ≥ 0.7` 的条目；低置信条目只作为 LLM 评审时的参考提示。
- **淘汰**：被后续证据推翻的条目标记 `superseded`，检索层过滤（保留历史可审计）。

### 10.3 有界 RSI：技能演进闭环（L2 → L3）

RSI 的核心思想——系统用运行中积累的经验改进自身的推理规则——在这里落地为
**"经验库 → 技能修订提案 → 离线验证 → 分级审批 → 版本生效"** 的受控闭环：

```
触发（每 N 个任务 或 经验库新增 ≥ M 条）:
  1. LLM 通读经验库增量 + 现行 SKILL.md
     → 产出 SkillRevisionProposal（diff 形式）：
       · 提示词改进（分析要点措辞、纠错策略细化）
       · 默认动作（如"S2 默认剔除索引列"）
       · 契约收紧建议（如泄漏判定加基数规则）
  2. 基准回归验证（离线，不碰线上任务）：
     历史配方 + 基准数据快照在新 SKILL.md 下重跑关键阶段
     → 全部不劣化才通过；任一劣化 → 提案驳回并回写经验（"该教训不可泛化"）
  3. 分级审批：
     · 低风险（提示词措辞、示例补充）→ 白名单自动生效
     · 中高风险（默认动作、流程/契约变更）→ 人工批准
     · 硬门禁阈值 → 仅允许收紧，且必须人工批准
  4. 生效 = SKILL.md 版本 +1（git 式 diff 存档），任一版本一键回滚
```

**与无约束 RSI 的区别（安全边界）**：
- **改进对象只有技能文档与策略，不是代码与门禁语义**——平台工具、硬门禁执行器、
  沙箱不可被 LLM 修改；
- **禁止运行中热改**：演进只在任务间离线发生，正在运行的任务不受影响；
- **单向收紧**：任何提案不得降低验收标准或放宽契约（防止"自我降低门槛式改进"）；
- **回归防线**：历史配方基准集保证演进不"漂移遗忘"已掌握的能力；
- **全程审计**：每次演进带 diff、依据的经验条目 ID、回归报告、审批人。

### 10.4 各阶段的经验注入点（汇总）

| 阶段 | 注入内容 |
|---|---|
| 任务启动 | L2 top-k 相近经验（domain+画像检索） |
| S1 | L1 上轮全链记忆；L2 中 cross-domain 高置信教训（如索引列处理） |
| S2 | L1 上轮 S2 报错-修复对（避免重犯）；L2 中本域脚本模式经验 |
| S3 | L1 上轮搜索配置与结果（缩小搜索空间）；L2 中本域算法偏好经验 |
| S4 | L1 上轮评审 surprises；L2 中评审 rubric 补充（低置信仅提示） |
| 任务收尾 | 蒸馏 L2 新条目（成功与失败都写入）；参与 L3 演进触发计数 |

## 十一、向导式编辑能力：用户逐步引导智能体（v0.4 新增）

> 需求：全自动之外，用户希望能**编辑并指导**生成过程——四步中的每一步都可以
> （但不必）注入选择与提示词；填得越多 LLM 越贴合业务意图，全不填即回到纯自动模式。
> 这是把"人工介入三处"扩展为**可选的步骤级引导**：介入强度由用户自己决定。

### 11.1 交互形态：四步向导（新建任务 / 编辑配方共用）

```
┌ 步骤 1 数据分析 ──┬ 数据预览表格：勾选列/行 + 行内备注（"这列是二轴扭矩，单轴行缺失属正常"）
│                   ├ 提示词输入（自由文本，可存为个人提示词模板复用）
│                   └ 常用提示词芯片：聚焦质量通道 / 关注时序漂移 / 怀疑某列泄漏 …
├ 步骤 2 特征工程 ──┬ 数据形态选择：表格 / 波形 / 混合（波形=含编码波形列需解码统计）
│                   ├ 列级指令：必须保留 / 建议剔除（带理由）
│                   └ 提示词（"优先派生比值类特征" "缺失用中位数+标记"）
├ 步骤 3 自动建模 ──┬ 算法多选（平台算法族清单，可不选=全族搜索）
│                   ├ 参数约束：trials / 时间预算 / CV 折数（可留空=LLM 按画像定）
│                   └ 提示词（"小样本优先轻量模型" "要求可解释性"）
└ 步骤 4 评估验收 ──┬ 上传新测试集（可选；不上传=平台自动留出）
                    ├ 指标阈值：精度/召回/F1/Acc/AUC 逐项填写（留空项不设门禁）
                    └ 评审重点提示词（"重点解释假阴性" "对比上一版模型的退化点"）
```

两种运行模式：
- **一次填完 → 全自动跑**（默认）：向导提交后按 v0.2/v0.3 流程自动迭代到验收或升级；
- **逐步确认**（可选开关）：每步执行完暂停，用户看该步产物（分析报告/特征脚本/候选指标）
  并可补充引导再放行下一步——适合首次摸索新场景，熟悉后切回全自动。

### 11.2 UserGuidance 契约（与三类契约并列，进 contracts/）

```json
{
  "analysis": {
    "column_notes": [
      {"column": "ACTUAL_TORQUE_TWO", "note": "二轴扭矩；单轴拧紧行缺失属正常，勿当数据缺陷"}
    ],
    "row_notes": [{"row_ids": [...], "note": "该批次换过夹具"}],
    "prompts": ["重点关注扭矩-目标偏差与上下裕度"],
    "suspect_focus": ["torque_deviation"]
  },
  "feature": {
    "data_shape": "tabular | waveform | mixed",
    "must_keep": ["TIGHTEN_DUAL_AXIS_DIFF"],
    "suggest_drop": [{"column": "ORDER_PROD", "reason": "工单号与质量无关"}],
    "prompts": ["派生特征优先比值/裕度类，剔除判定中间列"]
  },
  "modeling": {
    "algorithm_whitelist": ["lightgbm", "hist_gradient_boosting"],
    "param_hints": {"max_trials": 50, "cv_folds": 5},
    "prompts": ["召回优先于精度"]
  },
  "evaluation": {
    "custom_test_dataset_id": null,
    "metric_gates": {"recall_minority": 0.92, "f1": 0.88},
    "review_focus": ["解释假阴性样本的共同特征"]
  }
}
```

### 11.3 引导如何进入执行链（优先级与边界）

- **注入优先级：用户引导 > 跨任务经验（L2）> 技能默认（L3）**。用户明确的选择是硬约束：
  算法白名单直接限定 S3 搜索空间；`data_shape` 直接约束 S2 脚本的输入处理方式；
  `metric_gates` **替换**默认硬门禁阈值（用户就是业务方，可设可改，仍对 LLM 一票否决）。
- **column_notes/row_notes 是 S1 最有价值的输入**：它们随数据画像一起进 LLM 提示词，
  直接弥补"机器看不出业务语义"的缺口（如"缺失属正常"能阻止 LLM 误判数据质量）。
- **自定义测试集**：上传后作为 S4 的留出评估集（跳过自动切分），与生产分布对齐更可信；
  平台侧复用现有数据集上传通道，仅记录 `custom_test_dataset_id`。
- **提示词模板库**：自由提示词可保存复用（个人/项目级），与 L2 经验库分离——
  经验是系统蒸馏的客观教训，提示词模板是用户主观意图的沉淀，二者都注入但不混存。
- **与配方编辑合一**：向导同时是 Recipe 编辑器——载入已固化配方，各步骤预填当时配置，
  修改任意步骤即产生 Recipe 新版本（复用第十章的版本化与审计机制）。

### 11.4 平台侧新增（均为薄层）

| 项 | 说明 |
|---|---|
| 向导页（前端） | antd Steps 四步 + 数据预览勾选备注 + 算法多选 + 指标输入 + 测试集上传；与配方编辑复用同一表单 |
| UserGuidance Schema | contracts/ 新增第四契约；Agent Runner 校验后按 11.3 注入 |
| 任务暂停点 | 逐步确认模式：S1-S4 之间各设一个可暂停位（状态机 waiting_guidance） |
| 提示词模板 CRUD | 简单存取（用户/项目维度），不入经验库 |

## 十二、S5 服务化输出：从配方到闭环自动化与编排 API（v0.5 新增）

> 需求：智能体自我改进迭代完成、配方固化后，直接**按配方中的特征工程与最优模型**
> 自动生成两类线上服务——闭环自动化任务（方案 A）与应用编排服务图（方案 B），
> 并发布为可调用 API，端到端打通"建模 → 服务 → 报错回流 → 按配方重训 → 换模"。

### 12.1 服务化流水线（验收通过后自动执行，发布前人工批准一次）

```
配方固化（Recipe）
  ↓ ① 模型上线链（复用现有能力，零新代码）
     最优模型 Top-1 → 注册模型版本 → 批准 → 创建部署并启动（模型 API 自动上线市场）
  ↓ ② 生成闭环自动化任务（方案 A）
     按配方创建 demo-loop：deployment=新部署 · error_classes=缺陷类语义推导 ·
     特征工程=script 模式（配方定稿脚本）· 重训数据集=训练集+回流 · 阈值/比例取配方值
  ↓ ③ 生成应用编排（方案 B）
     从全局「闭环服务模板」实例化 7 算子服务图 → 按配方配置节点 → 发布版本 → 发布编排 API
  ↓ ④ 服务化验证（自动冒烟）
     编排 API 按发布特征清单调用 1 条（智能体用配方脚本对原始行做特征对齐）→ 200；
     闭环任务详情页可见、上传 1 行预测成功
  ↓ ⑤ 人工批准发布（唯一介入）→ 配方记录服务化资产，回流重训即按配方自动执行
```

### 12.2 关键映射：配方字段 → 服务配置（全部可自动推导）

| 配方字段 | 闭环自动化（方案 A） | 应用编排（方案 B） |
|---|---|---|
| `feature_script` | `feature_engineering_mode=script`（原始数据上传自动转特征） | 发布特征清单进 request_schema（调用方传特征行；智能体调用工具自动用脚本对齐） |
| 最优模型 lineage | 部署引用（①步上线的部署） | `load_model_artifact` 绑定最优模型 joblib 制品 |
| `target` 语义（如"0=不合格"） | `error_classes=["0"]`（缺陷类自动推导，不再人工判断方向） | `condition` 节点 value=缺陷类 |
| `acceptance_gates` | 告警阈值/重训阈值默认值来源 | retrain_threshold 节点 threshold_rows |
| 训练数据集 | 重训数据集多选（+回流数据集自动加入） | append_error_dataset / retrain 数据集 |
| （平台既有） | collect_correct 比例、换模部署=新部署 | swap_deployment=新部署 |

**缺陷类方向自动推导**是重点：S1 的 `target_semantics` 已识别"0=不合格，1=合格"这类语义，
S5 据此推导 error_classes——消除人工设错方向的风险（拧紧 0=不合格、电焊 fault=1 这类差异）。

### 12.3 与回流换模闭环的衔接

服务化产物天然进入现有闭环：线上推理报错行回流 → 积累到阈值 → **按配方自动重训**
（特征脚本+建模配置+门禁直接复用，不唤醒 LLM）→ 注册/批准/换模。即：
**智能体负责"造出第一版好模型并服务化"，现有闭环负责"持续变好"**；只有重训后硬门禁
失败时才唤醒智能体重新迭代（v0.3 迭代机制）。

### 12.4 向导与配方库的界面呈现

- 向导增加**第 5 步「服务化发布」**（验收通过后展示）：生成物预览卡——新部署信息、
  将创建的闭环任务配置摘要、将发布的编排 API 卡（含调用示例）——确认后一键发布；
- 配方库卡片增加**服务化资产徽标**（已绑定 部署/闭环任务/编排 API，点击直达）；
  配方新版本重新服务化时自动下线旧编排 API 并平滑换模到新部署；
- 任务档案页新增「服务化输出」区：三张资产卡 + 冒烟验证记录。

### 12.5 里程碑与风险补充

- **P3 追加交付**：拧紧配方端到端服务化（模型上线 + 闭环任务 + 编排 API 发布 + 冒烟通过），
  与电焊/拧紧手动搭建的两套服务对照一致；
- 风险：缺陷类推导错误 → 推导结果在向导第 5 步明示（"将把 0 判为报错回流"），
  发布批准时一眼可核；服务化覆盖 → 换用新版本时旧 API 自动下线、部署引用计数保护。

## 十三、智能体的复用、再编辑与优化总结报告（v0.6 新增）

> 需求：创建好的智能体（任务→配方）能复用、能再次编辑、能再次优化迭代；
> 每次优化完成必须产出**结构化总结**——优化了什么、发现了什么、擅长什么、
> 不理想之处与原因（缺数据/缺特征/缺领域知识…）。

### 13.1 复用与再编辑的三条路径

| 路径 | 入口 | 行为 |
|---|---|---|
| 复用于新数据 | 配方卡「用于新数据」 | 选新数据集 → delta 分析（差异小直接跑配方；差异大进完整迭代）→ 产出该数据专属的新任务（配方 lineage 指向母本） |
| 再编辑 | 配方卡「编辑」/ 向导载入配方 | 四步向导预填当时配置，改任意步 = 产生配方新版本（v1.2→v1.3，版本树可回滚） |
| 再优化迭代 | 配方卡「继续迭代」/ 任务卡「重跑」 | 携带历史全部轮次记忆 + 经验库增量，从"上次失败点"附近的策略继续（不是从零开始）；可改引导（如新增提示词、换算法白名单）后重跑 |

智能体任务与配方的关系：**任务是一次运行实例，配方是沉淀产物**。一个配方可派生多次
任务（新数据/再优化/回流重训），全部运行档案按 lineage 串联可审计。

### 13.2 优化总结报告（OptimizationReport，第五契约）

每次任务结束（无论验收/升级人工）自动生成，进入任务档案与配方版本说明，结构：

```json
{
  "task_id": "task-0023", "recipe": "tightening-v1.2→v1.3", "rounds": 2,
  "what_optimized": [
    "剔除 ID 索引列（轮1 评审发现重要性第3）",
    "TIGHTEN_UPPER/LOWER_MARGIN 由乘法缩放改为原始裕度（可解释性提升）"
  ],
  "findings": [
    "扭矩-目标偏差是第一主导特征（重要性 0.34，与 S1 预期一致）",
    "二轴差在双轴工位子集上区分度显著（AUC +0.05）"
  ],
  "strengths": [
    "不合格召回 0.944（门禁 0.92），满足漏检优先的业务要求",
    "14 维特征全部可物理解释，无黑盒特征"
  ],
  "unsatisfactory": [
    {"issue": "精确率 0.78 低于预期", "cause": "缺陷样本中约 12% 为边界贴限样本",
     "missing": "缺少螺栓规格分层的细粒度阈值列", "suggestion": "下轮补充 SPECIFICATION 编码或分组建模"}
  ],
  "metrics": {"before": {...}, "after": {...}, "delta": {"recall_minority": "+0.023"}},
  "next_hints": ["引入 SPECIFICATION 分组特征", "收集贴限样本的人工复判标签"]
}
```

- **unsatisfactory 必须带因果与缺失项**（缺什么数据/什么特征/什么领域知识）——这是用户的核心要求，
  也是下一轮迭代与 L2 经验蒸馏的直接输入；
- 报告由 LLM 从全链路档案（各轮报告/脚本/指标/评审）生成，指标数字一律取自平台工具，
  LLM 只做归因叙述；报告随配方版本永久存档。

## 十五、AI 对话的平台操作能力与硬边界（v0.6 新增）

### 15.1 能力形态：对话内工具调用（ChatTools）

对话集成平台操作工具白名单，用户自然语言 → LLM 选择工具 → 生成操作预览 →
**用户确认后执行**（写操作一律二次确认，读操作直接执行）：

| 工具（示例） | 类型 | 权限要求 |

| list_datasets / preview_dataset / profile | 读 | project.read |
| create_automl_task（发起自动建模） | 写 | resource.create |
| create_loop_task（创建闭环自动化） | 写 | resource.create |
| create_recipe_task（按配方跑智能体） | 写 | resource.create |
| publish_workflow_api / offline_api | 写 | 对应发布权限 |
| query_training_status / loop_status | 读 | project.read |

执行走**用户本人的权限**（对话只代操作，不提权）；操作结果回贴对话（含跳转链接）。

### 15.2 硬边界（不可协商，双层实现）

**第一层——白名单即边界**：对话工具是封闭集合（tools.md 注册制），没有"执行任意命令"、
"读写文件"、"访问数据库"类工具；LLM 无法越出工具集。

**第二层——显式禁则**（写入 SKILL.md 与系统提示，且平台侧无对应工具使其不可能）：
- ❌ 修改平台源代码、配置文件、数据库结构、系统功能；
- ❌ 修改/删除用户数据（删除类操作不进白名单；创建的可经对应页面删）；
- ❌ 变更权限、用户、密钥类管理操作；
- ❌ 任何绕过确认直执行的写操作。

安全审计：每次工具调用记录（会话/用户/工具/参数摘要/确认人/结果）入审计日志；
敏感工具（发布/下线）默认对非管理员关闭。

### 15.3 与智能体的关系

对话工具 `create_recipe_task` 等是智能体的**入口之一**：对话里说"帮我把这份数据按
拧紧配方跑一遍智能体" → 生成任务预览卡（数据/配方/门禁摘要）→ 确认 → 任务进入
智能体中心任务列表。对话是操作台，智能体中心是档案与迭代的家。

## 十六、知识库配置化与三大组件打通（v0.7 新增）

> 需求：知识库必须支持配置——用不用、用于哪个项目、哪个智能体等；
> 并打通知识库 ↔ 智能体自动迭代 ↔ AI 对话的正循环（域知识供给 → 迭代使用 →
> 经验回流 → 对话消费与生产）。

### 16.1 知识库绑定配置（KBBinding）

每个知识库档案增加配置层（独立于库内容，随时改随时生效）：

```json
{
  "kb_id": "kb-ef9331da",
  "name": "点焊标准法规",
  "enabled": true,
  "scope": {
    "projects": ["*"],
    "agent_tasks": "inherit",
    "chat": true,
    "agent_s1": true
  },
  "retrieval": {
    "top_k": 5,
    "max_total_chars": 6000,
    "min_score": 0.15,
    "trigger": "auto"
  },
  "sync": {
    "receive_experience": true,
    "experience_min_confidence": 0.85,
    "human_review": "auto"
  }
}
```

配置项语义：

| 配置 | 取值 | 说明 |
|---|---|---|
| `enabled` | bool | 总开关：关闭后对话/智能体/同步全部不可用 |
| `scope.projects` | `["*"]` / 项目 ID 列表 / `[]` | 全项目可用 / 仅列出的项目 / 不绑定（只剩显式指定） |
| `scope.agent_tasks` | `inherit` / `all` / 任务 ID 列表 | 跟随项目绑定 / 所有智能体任务 / 仅特定任务（如只在拧紧域任务启用） |
| `scope.chat` | bool | AI 对话可否绑定该库做 RAG |
| `scope.agent_s1` | bool | 智能体 S1 分析可否自动检索该库 |
| `retrieval.top_k` | int | 检索条数上限（省 token） |
| `retrieval.max_total_chars` | int | 注入提示词的字符预算 |
| `retrieval.min_score` | float | 相关性下限，低于不注入（防噪声） |
| `retrieval.trigger` | `auto` / `explicit` | auto=按列语义自动检索；explicit=仅任务显式指定才检索 |
| `sync.receive_experience` | bool | 是否接收跨域经验自动同步（16.3） |
| `sync.experience_min_confidence` | float | 接收同步的置信度门槛 |
| `sync.human_review` | `auto` / `pending` | 同步入库后直接可检索 / 标记待人工审核后才可检索 |

配置入口两处：知识库详情页（全局默认）+ 智能体向导 S1 步（任务级覆盖，
只读展示生效中的库与参数）。默认策略：新建库 `enabled=true, projects=[*],
chat=true, agent_s1=true, trigger=auto`——保持现状行为，不打扰存量库。

冲突合并：多库同时命中按 `score × 库权重`（库权重配置项，默认 1.0）排序取
top-k，注入时标注来源库，保证可追溯。

### 16.2 S1 检索链路具体化（引用可追溯）

```
S1 前置：query_kb(列基础名 + 注解语义 + 域假设关键词)
  → 各绑定库按各自 top_k / min_score 检索 → 合并去重 → 截断到 max_total_chars
  → 独立段落「【领域知识参考】（来源：库名/文档名/片段ID）」注入 S1 提示词
AnalysisReport 新增字段：
  "kb_citations": [
    {"kb": "点焊标准法规", "doc": "GB_T 1511", "chunk": "c-218", "score": 0.41,
     "used_for": "确认飞溅等级判定与标准第 5.2 条一致"}
  ]
```

- 引用片段 ID 落档：任务档案与配方保留 kb_citations，评审时可核对"S1 的预期
  重要特征是否真来自标准条款"——防 LLM 假引用；
- 检索为空时 S1 照常运行（不硬依赖知识库），报告标注 `kb_citations: []` +
  提示"本域无知识库命中，建议上传工艺文档"。

### 16.3 经验库 ↔ 知识库 双向同步

**正向（系统 → 知识）**：L2 蒸馏时 `generality=cross-domain` 且
`confidence ≥ experience_min_confidence` 的条目自动格式化为 Markdown 写入该库
"平台经验"分区（含证据链与来源任务链接），按 `human_review` 决定直接可检索
还是待审后可检索。

**反向（人 → 系统）**：用户在知识库页修订或否决该经验文档（文档头加
`experience-override: retired` 标记）→ 平台检测标记回写 L2 条目状态
（active → retired / superseded），检索层即刻过滤——"系统蒸馏 → 人审 → 回流"
闭环，即十三章 RSI 人工闸门的落地界面。

同步幂等：经验 → 文档以条目 ID 为键（文档名 `经验 exp-0042`），重复蒸馏更新
不重复建；被否决条目不再同步。

### 16.4 对话洞察沉淀（save_insight）

- AI 对话新增白名单工具 `save_insight(text, scope)`：对话说"记一下：二轴扭矩
  缺失在单轴工位是正常的"→ LLM 提取 `{situation, lesson, action}` → 用户确认 →
  存为**项目级经验条目**（confidence=0.70，标记人工来源），该项目智能体下轮
  S1 自动注入；
- 反向引用：对话回答"上次建模为什么失败/擅长什么"→ 工具
  `query_recipe_reports` 从配方档案取 OptimizationReport 结构化回答；
- 边界不变：save_insight 是写操作（二次确认）、走项目权限、写入内容入审计。

### 16.5 三组件正循环总图

```
        ┌─ 知识库（配置化绑定） ──┐
        │  工艺文档/标准/法规      │──S1 检索(可追溯引用)──→ 智能体自动迭代
        │  平台经验分区(同步来的)  │←─跨域经验自动同步(≥门槛)──  (四步+S5)
        └────────▲───────────────┘         │
                 │ 人审/否决(回流RSI闸门)    │ 优化报告
                 │                         ▼
        AI 对话 ──save_insight(项目级经验)──→ 经验库
        (绑库RAG/工具操作) ←─query_recipe_reports─ 配方档案
```
